# Разворачивание бота на VPS

Инструкция для Windows (команды `ssh`/`scp` уже встроены в Windows 10/11 —
отдельно ничего ставить не нужно; PowerShell открывается через меню Пуск).

## 1. Арендовать сервер

Рекомендация: **Ubuntu 22.04 LTS**, минимум **2 ГБ RAM / 2 vCPU / 30 ГБ SSD**
(нужно с запасом — устанавливается PyTorch для модели эмбеддингов).

**Берите площадку за пределами России.** Это не вкусовщина: у российских
провайдеров доступ к `api.telegram.org` закрыт, и бот на таком сервере
просто не сможет получать сообщения — в логах будет бесконечное
`Failed to resolve 'api.telegram.org'`. Обходится это только прокси, то
есть лишним звеном, которое тоже может отвалиться. На зарубежном сервере
проблемы нет вовсе.

Подойдут Нидерланды, Германия, Финляндия — ближайшие к России площадки с
низкой задержкой. Провайдеры с оплатой картой РФ и такими локациями:
Aeza, VDSina, Zomro, HostKey; из зарубежных — Hetzner, Contabo (оплата
сложнее). Конкретный выбор не принципиален.

Мини-приложение на этот же сервер поставим на шаге 6: пользователи будут
открывать его по вашему домену, и с зарубежной площадки оно открывается
нормально.

После создания сервера у вас будет:
- IP-адрес сервера (например, `185.1.2.3`)
- пароль root (или SSH-ключ — если предложат, проще пока выбрать пароль)

## 2. Загрузить проект на сервер

В PowerShell на своём компьютере, из папки, куда вы распаковали архив
проекта (замените `185.1.2.3` на свой IP):

```powershell
scp -r .\tarot_astro_bot root@185.1.2.3:/opt/tarot_astro_bot
```

Введите пароль root, когда попросит. Если `scp` ругается на новый хост —
согласитесь (`yes`) при первом подключении.

## 3. Подключиться и запустить установку

```powershell
ssh root@185.1.2.3
```

Дальше — уже на сервере (внутри SSH-сессии):

```bash
cd /opt/tarot_astro_bot
chmod +x deploy/setup.sh
bash deploy/setup.sh
```

Скрипт сам поставит Python, зависимости, соберёт векторную базу (если её ещё
нет — но она уже в архиве, так что этот шаг обычно пропустится) и настроит
автозапуск через systemd.

## 4. Вписать токен бота

```bash
nano .env
```

Впишите строку (замените на свой токен от @BotFather):

```
TELEGRAM_BOT_TOKEN=123456789:AA...
```

Сохраните: `Ctrl+O`, `Enter`, затем `Ctrl+X`.

## 5. Запустить бота

```bash
systemctl start tarot-astro-bot
systemctl status tarot-astro-bot     # должно быть "active (running)"
journalctl -u tarot-astro-bot -f     # логи в реальном времени, Ctrl+C — выход
```

Если всё хорошо, в логах будет строка вида `Бот запущен как @имя_бота`.
Напишите боту в Telegram — должен ответить.

## 6. Мини-приложение: домен и HTTPS

Без этого шага бот работает, но кнопка «✨ Приложение» не появится: Telegram
открывает мини-приложения **только по HTTPS и только с сертификатом
настоящего центра сертификации**. Ни `http://`, ни самоподписанный
сертификат, ни временный туннель `trycloudflare` для постоянной работы не
годятся — у временного туннеля адрес меняется при каждом запуске, а адрес
приложения прописан и в кнопке меню бота, и во всех кнопках, уже
отправленных людям в чаты.

**Что нужно купить.** Домен — от 200 до 900 ₽ в год, любой регистратор.
Дальше в его панели создайте A-запись для поддомена:

```
app.вашдомен.ru    A    185.1.2.3
```

(вместо `185.1.2.3` — IP вашего сервера). Запись расходится по интернету
от нескольких минут до часа; проверить можно с домашнего компьютера:

```powershell
nslookup app.вашдомен.ru
```

Пока в ответе не появится IP сервера, дальше идти бессмысленно: сертификат
выдаётся по факту владения доменом.

**Открыть порты.** Если на сервере включён фаервол:

```bash
ufw allow 80/tcp     # нужен Let's Encrypt для проверки домена
ufw allow 443/tcp    # по нему работает само приложение
ufw status
```

Порт 8080 наружу открывать **не нужно и нельзя**: приложение слушает только
петлевой адрес, а наружу смотрит через Caddy — то есть всегда по HTTPS.

**Поставить Caddy.** Он получает сертификат Let's Encrypt сам и сам его
продлевает:

```bash
apt install -y debian-keyring debian-archive-keyring apt-transport-https curl
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' \
  | gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' \
  | tee /etc/apt/sources.list.d/caddy-stable.list
apt update && apt install -y caddy
```

Конфиг уже лежит в проекте — скопируйте и впишите свой домен вместо
`app.example.com`:

```bash
cp /opt/tarot_astro_bot/deploy/Caddyfile /etc/caddy/Caddyfile
nano /etc/caddy/Caddyfile
systemctl reload caddy
```

Через полминуты проверьте в браузере `https://app.вашдомен.ru` — должна
открыться страница приложения с замком в адресной строке.

**Сказать боту его адрес.** В `.env` добавьте строку и перезапустите бота:

```bash
nano /opt/tarot_astro_bot/.env
```

```
WEBAPP_URL=https://app.вашдомен.ru
```

```bash
systemctl restart tarot-astro-bot
journalctl -u tarot-astro-bot -n 20
```

В логе появится `Мини-приложение: https://app.вашдомен.ru`, а в чате с
ботом рядом со строкой ввода — кнопка «✨ Приложение».

**Адрес больше не меняйте.** Он прописывается в кнопку меню и во все
кнопки, уже отправленные людям. Сменить домен — значит сломать кнопки во
всей истории переписки.

## Безопасность после установки

**Проверьте, что бот работает не от root.** Скрипт заводит системного
пользователя `tarotbot`; убедиться можно так:

```bash
systemctl show tarot-astro-bot -p User
ps -o user=,cmd= -C python | grep bot.py
```

Должен быть `tarotbot`, не `root`. Привилегии боту не нужны, а уязвимость
в любой из сотен транзитивных зависимостей под root означала бы
компрометацию всего сервера.

**Права на `.env`:**

```bash
ls -l /opt/tarot_astro_bot/.env      # ожидаем -rw-r----- root tarotbot
```

Если права шире — `chmod 640 .env && chown root:tarotbot .env`. Токен из
этого файла даёт полный контроль над ботом и доступ ко всей переписке
пользователей.

**Анкеты клиентов.** Имя, дата, время и город рождения лежат в
`store/profiles.json` — это персональные данные. Каталог создаётся
скриптом установки с правами `700` на пользователя бота, в systemd-юните
он отдельно открыт на запись (`ReadWritePaths`), а в резервные копии кода
не попадает: `store/` в `.gitignore`. Бот сам удаляет анкеты, к которым не
обращались 180 дней (`RETENTION_DAYS` в `bot/store.py`); клиент стирает
свои данные командой `/reset`. Если политика хранения у вас строже —
уменьшите `RETENTION_DAYS`, ничего больше менять не нужно.

**Ротация журнала.** Бот пишет в journald, а тот по умолчанию хранит логи,
пока не кончится место. В логи попадают номера чатов — это персональные
данные, и держать их вечно незачем. Ограничьте срок хранения глобально
(отдельной настройки на юнит в systemd нет):

```bash
sudo nano /etc/systemd/journald.conf
```

```ini
[Journal]
MaxRetentionSec=7day
SystemMaxUse=500M
```

```bash
sudo systemctl restart systemd-journald
```

**Установка из lock-файла.** Если нужен воспроизводимый набор версий
(и защита от подмены пакета в PyPI), ставьте зависимости так:

```bash
./venv/bin/pip install --require-hashes -r requirements.lock.txt
```

Lock-файл в репозитории собран на Windows; для Linux-сервера пересоберите
его на самом сервере:

```bash
./venv/bin/pip install pip-tools
./venv/bin/python -m piptools compile --generate-hashes \
    --output-file requirements.lock.txt requirements.txt
```

## Полезные команды на будущее

```bash
systemctl restart tarot-astro-bot    # перезапустить (например, после обновления кода)
systemctl stop tarot-astro-bot       # остановить
journalctl -u tarot-astro-bot -n 100 # последние 100 строк логов
```

## Обновление базы знаний или кода

Если вы поменяли данные в `data/` или сам код:

```powershell
scp -r .\tarot_astro_bot root@185.1.2.3:/opt/tarot_astro_bot
```

(перезапишет файлы на сервере; venv и .env не пострадают, так как scp -r
просто докопирует/обновит файлы поверх), затем на сервере:

```bash
cd /opt/tarot_astro_bot
./venv/bin/python scripts/generate_combinations.py
./venv/bin/python scripts/build_vectorstore.py
systemctl restart tarot-astro-bot
```
